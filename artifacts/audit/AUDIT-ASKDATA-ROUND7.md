## 五、随结论一起披露的两点（不影响「本轮通过」，但建议写进材料）

### 5.1 模型路径仍未验证，且围栏没有 fan-out 规则（未验证风险，非已确认缺陷）

这轮（以及前几轮）所有 fan-out 处理都做在**规则路径**（`planner.ts`）。模型路径的 SQL 只过 `guardrail.ts` 的三层校验，而围栏里**没有任何一条规则能识别「SUM 被连接放大」**——`inspectResult` 只查负值 / 量级 / 比率 / 客户数超全库（`guardrail.ts` 结果层），语义层只查表名列名。因此：如果接上密钥后模型自己写出 `SELECT SUM(a.total_asset) ... JOIN cust_holding h ...`，它会 `passed=true` 被直接执行并返回放大的数字。

我**没有密钥，无法验证**这条；它属于"未验证风险"而不是"已确认的错误路径"，所以不改变第 2 问的结论。建议二选一：
- 材料里的措辞限定为「**规则路径**已无已知的错误数字路径；模型路径需在密钥就绪后按同一批问法复测」——这样最严谨；
- 或者在围栏里加一条**提醒级**规则（例如：SELECT 里出现对 1:1 表的 SUM，而 FROM 里存在 1:n 表时给 G-RES-08 提醒），至少让这类 SQL 在审计里可见。

### 5.2 一条「少答一列」的完整性小问题（不是错数）

- 复现：「**总资产超过 1000 万的客户的总资产与持仓市值**」→ 实际只返回 `{持仓市值合计: 7600717234}`，**总资产这一列被丢掉了**。
- 原因：`planner.ts` 里「『总资产超过 X』是筛选条件而不是指标（除非句中出现合计/总额/平均）」这条既有启发式在这个句子上误判——用户确实同时要了总资产。
- 数字本身是对的（7,600,717,234 = 我的独立值），只是少答一列；把问法写成「总资产**合计**与持仓市值」即正常（已实测 = 11,091,740,855 / 7,600,717,234 ✓）。
- 影响：属于"少答"，不是"错答"，也不在你要的那一类里。若要修，可把该启发式的触发条件收紧为「『总资产超过 X』后面没有再出现与其它指标的并列（『与/和/、』）」；若不修，建议作为第 7 条已知限制（完整性问题）附在材料里。
