## 三、新发现：两条仍会主动输出错误数字的路径

### F1 多表连接的 SUM fan-out（未修，属新发现）

**触发条件**：一次查询里同时出现**粒度不同的两张表**（一对一表 × 一对多表，或两张一对多表）。`COUNT(DISTINCT c.cust_id)` 免疫，但 `SUM` 会被连接行数放大；`planner.ts` 用 `cust_info` 做驱动表只能保证客户数不被放大，挡不住这一条。

实测（期望值由我在单表上独立算出）：

| 问法 | 期望 | 规划器实际 | 偏差 |
|---|---|---|---|
| 客户总资产与持仓市值 | 总资产 11,780,575,938 / 持仓市值 8,066,582,414 | **30,383,275,047** / 8,066,582,414 | 总资产 **+157.9%** |
| 总资产与近 90 日交易金额 | 总资产 11,780,575,938 / 交易金额 3,902,881,033 | **15,211,350,806** / 3,902,881,033 | 总资产 **+29.1%** |
| 持仓市值与近 90 日交易金额 | 持仓市值 8,066,582,414 / 交易金额 3,902,881,033 | **9,748,321,627** / **10,185,319,646** | 持仓市值 +20.9%、交易金额 **+161.0%** |
| 总资产与日均资产与持仓市值 | 11,780,575,938 / 10,942,305,697 / 8,066,582,414 | **28,207,242,221** / 8,066,582,414 / **30,383,275,047** | 两个值错 |

生成的 SQL 形如 `FROM cust_info c JOIN cust_holding h ON ... JOIN cust_asset a ON ...`，`SUM(a.total_asset)` 被每客户持仓条数重复计入。

**对照组（单表组合，全部正确）**：持仓市值 + 持仓成本 ✓、总资产 + 日均资产 ✓、客户数 + 持仓市值 ✓。

**为什么之前几轮没发现**：三档语料里没有"两个不同粒度表的多指标"题；结果层也没有任何规则能识别连接放大（只查负值/量级/比率/客户数超大）。**它不是本轮改动引入的**，是自 ROUND1 起就存在的路径，我在本轮的多指标排查中才测到。

**修复方向**：多指标时把每个指标改写为标量子查询（`SELECT (SELECT SUM(total_asset) FROM cust_asset) AS 总资产, (SELECT SUM(market_value) FROM cust_holding) AS 持仓市值`），而不是把两张表并列 JOIN；并在 `planner.test.ts` 补一条"两个不同粒度表的多指标"断言。

### F2 未枚举的限定条件被忽略，仍返回客户总数（未修，与已修的 N1 同族）

**触发条件**：问题里有「客户」+「多少/几」这类数量词，但限定条件用的是域外词表尚未枚举的说法（或元数据里根本没有的字段）。此时 `planner.ts:312` 的兜底会命中，直接返回客户总数。

实测 6/6 全部误答：

| 问法 | 规划器行为 |
|---|---|
| 有多少位客户在犹豫 | 客户数 1000 |
| 有多少客户打算换券商 | 客户数 1000 |
| 有多少客户对我们不满意 | 客户数 1000 |
| 有多少客户最近不太活跃 | 客户数 1000 |
| 有多少客户可能会关户 | 客户数 1000 |
| 有多少客户是潜在的高价值客户 | 客户数 1000 |
| （对照）有多少客户投诉了 | 拒答 ✓ |

**为什么重要**：「关户/换券商」其实就是「流失」的同义说法，只因为没枚举到那个词就退回成客户总数——比拒答更糟，而且是**枚举式词表的固有上限**（永远补不完）。

**修复方向**（二选一，都很便宜）：
1. 收紧兜底：只有在问题包含数量词、已登记实体**且不含任何未登记名词**时才回退到客户数（可用"把问题里已登记的实体与属性词全部剔除后，是否还剩中文词"做粗判）；
2. 保留兜底但在 `notes` 与界面显式标注"仅按客户总数作答，问题中的其它限定条件未被理解"，并把它计入评测的"降级作答"一档。

## 四、一条主动澄清（避免我误报）

ROUND3 我点到过「语料 q40 的黄金答案带 fan-out、AVG 被持仓条数加权」的可能性。本轮我把它算清楚了，**结论是我当时的怀疑不成立**：

- 语料 q40 的 `AVG(a.total_asset)` 带 join fan-out，但与"客户等权平均"相比偏差只有 **+1.16%（高净值）/ −0.43%（普通）**，在 2% 容差内，不构成错误数字。
- 我先前拿到的 ~22% 差异，来自我的对照口径不同（我按"每客户先算平均持仓市值"= 客户等权，而 q40 是"每持仓等权"），**是我的对照写法不同，不是 q40 的缺陷**。
- 结论：q40 不需要改；**F1 的问题只出现在 SUM 型多指标，不适用于 AVG 型**（AVG 对同一客户内的重复只表现为加权，量级不变）。

## 五、仍然存在的已知限制（可直接写进材料）

按你关心程度排列：

1. **多表连接的 SUM fan-out（F1）**：一次查询里出现两张不同粒度的表时，`SUM` 会被连接行数放大（实测 +20.9% ~ +161.0%）。触发问法形如"总资产与持仓市值""持仓市值与近 90 日交易金额"。**未修**。
2. **未枚举的限定条件被忽略（F2）**：域外词表是枚举式的，"关户/换券商/不太活跃"这类未枚举说法仍会退回客户总数。**未修**。
3. **CTE 内的跨表幻觉字段可穿透**：`WITH x AS (SELECT market_value FROM cust_info) ...` 会放行，但 `guardrail.ts:256-262` 已用 **G-SEM-07 提醒**显式留痕并写入审计（ROUND3 G2，已披露）。
4. **内层子查询的超限 LIMIT 不收敛**：`SELECT * FROM (SELECT ... LIMIT 5000) LIMIT 10` 放行，外层 10 行兜住结果集但内层扫描量不拦（ROUND3 G4）。
5. **结果层只提醒不拦截**：`inspectResult` 无拦截分支（申报书与 README 已如实标注）。
6. **模型路径未实测**：无密钥，全部数字来自规则路径。
7. **非流水指标上的时间窗被忽略**：如「近 30 日的持仓市值」不含时间条件（持仓表无历史快照，属设计取舍，建议在返回体或界面注明）。
8. **`detailSubquery` 的类型守卫偏弱**：`detailTimeColumn` 仍是 `Record<string, string>`，写错表名不会被 TS 拦住、且会静默丢掉时间窗；当前三个调用点都正确，**无实际行为问题**（ROUND3 G3）。
9. **语料自造、样本内**：三档 100% 只代表"确定性可复现"，不代表开放问法能力（材料已标注，且已写入我独立探针 8/8 这一交叉证据）。
10. **域外词表按关键词匹配**：不做语义判断，因此既有 F2 的漏拦方向，也可能有少量误拦方向（本轮已消除「电话」这一例）。
