## 三、阻断级

### A1. 100% 的自测准确率是「样本内拟合」，不是能力

**现象**：`scripts/eval-ask.ts` 会同时跑样本内与留出集，两者现在都是 100%。

**证据**：
- 时间线：语料 18:49:18 → 规划器 18:49:5x / 18:50:2x / 18:50:38（三版）→ 留出集 18:50:01。留出集比规划器的第二、三版**更早**定稿。
- 规划器 pattern 直接使用语料原词：`/在售产品/` 对语料 q07「在售产品一共有多少只」；`/客户经理.{0,6}(多少|几|人数|数量)/` 对 q14「客户经理一共有多少人」；`/资金流水|流水条数|流水记录|流水数量/` 对 q16「资金流水一共有多少条」；`/持仓成本|持仓总成本|成本合计|总成本/` 对 q18「客户持仓的总成本是多少」；`/平均年龄|年龄的?平均/` 对 q03「客户的平均年龄是多少」。
- 同一 50 题的历史准确率：18:47 实测 18/50（36%），18:49 实测 44/50，18:49:34 实测 42/50，18:50:09 实测 50/50。数据与题目都不变。

**影响**：申报书写「执行准确率 100%」会被评委直接追问留出方式；赛题口径下真正的留出集是组织方提供的问答对（保密协议通过后才发放），我们手上的是自造题且在样本内迭代。

**修复方向**（择一或组合）：
1. 冻结语料：规划器定稿后不得再看留出集内容；留出集最好由参赛团队成员按自己的表述习惯手写，且写在与规划器不同的用词上。
2. 材料里同时写「样本内 50/50 + 冻结留出集 X/Y」，并明确标注「组织方问答对到位前，该数字仅代表样本内自检」。
3. 保留一组必然失败的对照问法（例如完全不含元数据用词的口语化提问），让指标存在失败的可能。

### A2. 安全围栏的「列合法性」不按表校验 → 幻觉字段可穿过

**证据**：`lib/analytics/guardrail.ts:131-137` 把所有表的列并成一个 `knownIdentifiers` 全集。
**实测**：`SELECT gender, market_value FROM cust_info LIMIT 10` → `passed: true`（`market_value` 只属于 `cust_holding`）。
**影响**：赛题攻关任务二点名「表、指标、结果的合法性验证」，列级验证目前不成立；漏拦的 SQL 只能靠执行报错兜底，用户得到的是「执行失败」而非「哪一列不合法」。
**修复方向**：由 `FROM/JOIN` 建立 别名→表 映射，用该表的列集合校验该别名下的列；裸列名先按参与表求交集，落在交集外即拦截。

### A3. 提示词鼓励 `WITH`，围栏必然拦截 `WITH`

**证据**：`lib/analytics/agent.ts:43` 要求「sql 必须是单条 SELECT 或 WITH」；`guardrail.ts:67` 放行 WITH 前缀；`guardrail.ts:110-121` 把 `FROM <CTE名>` 当表名与九表白名单比对。
**实测**：`WITH x AS (SELECT cust_id FROM cust_info) SELECT COUNT(*) FROM x LIMIT 5` → `passed: false`（G-SEM-01 + G-SEM-03 双重拦截）。
**影响**：模型只要用 CTE 必被拦 → 降级到规则路径。而赛题明确要求「复杂查询（多表多指标、跨主题域）」，这类查询最需要 CTE。等于在提示词里把模型引向必然被拦的写法，结构性压低模型路径成功率与端到端准确率。
**修复方向**：先抽出 `WITH a AS (...), b AS (...)` 的 CTE 名并入白名单再校验；或明确禁止 WITH 并同步删掉提示词里的 WITH，二者取其一。

### A4. 「指标合法性验证」是死代码

**证据**：
- `agent.ts:66` 收集模型声明的 `metrics`，但 `agent.ts:116-118` 只取 `sql/tables/explanation`，`metrics` 被丢弃；
- `guardrail.ts:148` 用 `sql.includes(metric.name)` 在 SQL 文本里搜指标的英文注册名——`net_inflow_90d`、`holding_count` 这类构造名不会出现在 SQL 里；
- `guardrail.ts:150` 的触发条件是 `metric.tables.length === 0`，而 13 个指标全部声明了 tables（`metadata.ts:23-78`）→ 该分支恒不触发。

**影响**：赛题三大攻关任务之一就是「减少大模型幻觉」，其中「指标验证」这一层在代码上不存在。材料不能写「已实现指标合法性验证」。
**修复方向**：校验模型声明的 `metrics` ⊆ 指标注册表（未登记即拦截/标注）；再校验指标依赖表 ⊆ SQL 实际引用的表。

### A5. 元数据术语与数据仍不一致：高净值标签 ≠ 术语定义

**证据**：
- `metadata.ts:84`：「高净值客户 = 总资产不低于 1000 万元的客户，与客户信息表的客群标签口径一致」；
- `seed.ts:14` 阈值 `analyticsHighNetWorthAsset = 10_000_000`；`seed.ts:106` 派生 `highNetWorth`；但 `seed.ts:118` 的三元表达式让 沉默/活跃 优先于 高净值。

**实测**（快照 seed 20260830 / 1000 客户）：
- `cust_tag='高净值客户'` **107 人**；`total_asset ≥ 1000万` **198 人**；**≥1000万 却没打高净值标签 91 人**。
- 术语「活跃客户 = 近 90 日有交易」→ **918 人**，而 `cust_tag='活跃客户'` **310 人**。
- 术语「沉默客户 = 近 90 日无交易且无流入」→ **54 人**，而 `cust_tag='沉默客户'` **159 人**。

**影响**：模型按元数据口径（≥1000万）写 SQL，与按 `cust_tag` 写的黄金答案必然不一致 → 评测把正确答案判错；同时「AI 友好的元数据」（攻关任务一）被自己的数据否定。
**修复方向**：让 `cust_tag` 与术语定义严格等价（高净值/活跃/沉默互斥且按口径派生），或把术语定义改成 `cust_tag` 口径并删掉「与客群标签口径一致」这句。

## 四、重要

### B1. 结果层拦不住「结果荒谬」
- 证据：`guardrail.ts:167-215` 只做 行数 / 列数 / 空结果 / 金额负值 / 比率越界 五项，且**全部是「提醒」，没有拦截**。
- 实测：`inspectResult(['客户数'], [{客户数: 5000}])` → `[]`（全客群才 1000 人）；`inspectResult(['持仓市值'], [{持仓市值: 1e15}])` → `[]`。
- 影响：赛题要求「降低大模型幻觉带来的影响」，这一层目前几乎没有兜底能力。
- 修复方向：加量级/基数交叉校验（客户数 ≤ `cust_info` 行数、持仓市值 ≤ 总资产、SUM 与明细对账、比率字段与定义域对齐）。

### B2. LIMIT 校验可被子查询里的 LIMIT 顶替
- 证据：`guardrail.ts:94` 只取第一个 `LIMIT n`。
- 实测：`SELECT * FROM cust_info WHERE cust_id IN (SELECT cust_id FROM cust_trade LIMIT 5)` → `passed: true`，且外层未补 LIMIT。
- 影响：结构层「必须带行数上限」失效；大表全扫直接打在「体验性 20%」上。
- 修复方向：按括号深度定位最外层语句，只认最外层的 LIMIT。

### B3. 函数白名单过窄导致误拦，且拦截文案错误
- 证据：`guardrail.ts:42-46` 的 `allowedFunctions`。
- 实测被误拦（`passed:false`）：`LENGTH`、`UPPER`、`IFNULL`、`NULLIF`、`GROUP_CONCAT`、`CURRENT_DATE`、`datetime`、`OVER`（窗口函数）；`REPLACE(cust_name,'a','b')` 还额外触发 `G-STRUCT-03 禁止写操作`（把函数名当成写关键字）。
- 影响：误拦 → 降级到规则路径；且 finding 把合法函数说成「臆造字段/写操作」，审计记录不可信。
- 修复方向：补齐常用函数（SUBSTR / LOWER / TRIM / LTRIM / RTRIM / IFNULL / NULLIF / LENGTH / PRINTF / DATETIME / JULIANDAY / CURRENT_DATE / CURRENT_TIMESTAMP / GROUP_CONCAT / OVER / PARTITION / ROW_NUMBER 等）；`REPLACE` 只在 `REPLACE INTO` 或语句起始位置判为写操作。

### B4. 验收口径未定义，「准确率」可以算出任何数
- 证据：计划只定义「数值类相对误差 ≤2%」「名单类 Jaccard ≥0.95」；语料 50 题里有 17 条 `kind: 'rows'`（分组多指标），比对规则完全没定义。
- 实测：同一份结果，用「按列序展开」比得 44/50；用「按首列分组键对齐、忽略列名与列序」比得 42/50 与 50/50。同一次运行换个比对方式能差 6 个百分点以上。
- 影响：材料里报的准确率依赖比对实现，评委无法复核。
- 修复方向：把比对规则写进 `scripts/eval-ask.ts` 并在材料中一并说明（建议：分组结果按分组键对齐、数值列按 ≤2% 相对误差、忽略列名与列序、行数必须一致）。

### B5. 「前 N 名」语义被当成 LIMIT
- 证据：planner 里 `topN = /前\s*([0-9]+)\s*(名|位|个|条|大)/`，随后只用 `Number(topN[1])` 作为 LIMIT；分组分支固定 `ORDER BY 1`（按第一个维度列排序）。
- 实测（18:49:20 快照）：留出集 h09「各客户经理名下的主办客户数（前 5 名）」、语料 q34「各客户经理名下的客户数（前 10 名）」生成 `GROUP BY … ORDER BY 1 LIMIT N`，语义是「按名称排序取前 N 行」，而正确语义是「按客户数降序取前 N 行」。
- 影响：给出「看起来对、实际选错行」的结果，人工复核与自动评测都容易漏过。
- 修复方向：命中「前 N 名」时，ORDER BY 改为第一个聚合列降序。

### B6. 取数 Agent 未接入系统（功能可达性）
- 证据（18:50:46 复核）：`lib/harness/tools.ts` 仍是 8 个工具（`rg -c "name: '"` = 8），无任何 `metadata.*` / `analytics.ask`；`app/api/analytics/ask/route.ts:1` 仍 `import { answerAsk, askExamples } from '../../../../lib/analytics/ask'`（旧的沙盘客户池问答）；`app/api/analytics/` 下只有这一个 route；`components/sandbox-app.tsx` 的 AskView 不出现「元数据 / 安全围栏」字样。
- 影响：赛题三条攻关任务在可运行系统里看不到，评审跑系统只能看到沙盘。
- 修复方向：注册 4 个 metadata 工具 + `analytics.ask`；新增 `/api/analytics/ask`（返回 sql / guardrail / mode）、`/api/analytics/metadata`、`/api/analytics/review`；AskView 改为五步链路。
- 备注：审计期间 `scripts/eval-ask.ts` 出现（含样本内/留出集双轨与 `eval:ask` 脚本命令），说明主智能体正在补评测侧，需在下一轮复核。

### B7. 首次请求装载 13,622 行 / 341 次 batch，且每次问答重复跑 15 条 DDL
- 证据：`agent.ts:95` 每次问答都调用 `ensureAnalyticsData`；装载循环按 40 行一批（341 批）；DDL 为 9 表 + 6 索引 = 15 条。
- 实测：内存库首次装载 95 ms，幂等第二次 0 ms；D1 上的真实延迟未实测。
- 影响：部署后首次请求延迟不可控；评测脚本若每题新建库会重复付这个成本，直接打在「体验性 20%」。
- 修复方向：把装载拆成一次性初始化（脚本/接口），问答路径只做存在性检查。

## 五、一般

### C1. 九表与赛题表名一一对应，但列级对齐无法核验
赛题原文（`附件1-赛题要求.docx` 第 121 行）只给出九个中文表名。`schema.ts` 九张表与之对应（已核查通过），但赛题未给列定义 → 材料只能写「按维度建模自建、官方数据到位后替换装载层」，不要写「完全对齐官方口径」。

### C2. 赛题提到命题单位「已设计一套元数据表」
赛题第 111 行写明命题单位已有「元数据表（表信息、列信息、业务知识、指标）」，而我们的元数据是 TS 常量。建议补一张 `meta_*` 表，或在材料中说明「元数据以代码 + 工具双形态提供」。

### C3. 合成数据含未来日期
`seed.ts:11` 的 `analyticsSeedReferenceDate = '2026-09-30'` 晚于今天（2026-09-19），`stat_date` 与部分 `trade_date` 落在未来。规则路径已改用固定快照日（planner 的 `analyticsSnapshotDate = '2026-09-30'`），跨天漂移已解决（已核查通过），但「数据里出现未来日期」本身建议在材料中说明。

### C4. 字符串字面量里的 `--` 被误判为注释
实测：`SELECT * FROM cust_info WHERE cust_name LIKE '%--%' LIMIT 5` → `G-STRUCT-04 拦截`。注释检测（`guardrail.ts:86`）跑在原始 SQL 上，应先剥离字符串字面量再查注释。

### C5. 时间窗口在两个流水表之间用 `else if`，需复核
planner 的窗口逻辑是 `if (tables.has('cust_trade')) … else if (tables.has('cust_cashflow')) …`，且 `windowCondition` 的入参类型只有 `cust_trade | cust_cashflow`。当问题同时涉及交易表与流水表时，只有其中一张会带上时间窗。语料里没有这类题（所以测不出来），建议补一条正例。

### C6. 两套 ask 并存
`lib/analytics/ask.ts`（旧：沙盘客户池指标，`AskMetric = 客户数|平均回撤|平均恐慌|…`）与 `lib/analytics/agent.ts`（新：九表取数）概念同名并存，且旧模块仍是对外接口的实现。建议改名（如 `sandbox-ask.ts`）以免评审与后续维护混淆。

### C7. 测试覆盖缺口
- 两份语料在仓库内没有测试引用（`rg` 只在 `scripts/eval-ask.ts` 命中）。
- `ensureAnalyticsData` / `buildAnalyticsSeed` 无单元测试：九表行数、确定性、口径一致性都没进测试（`guardrail.test.ts` 只覆盖围栏与元数据结构）。
- 围栏测试缺少负例：无「跨表幻觉列」「CTE」「子查询 LIMIT」「结果荒谬」用例——这正是 A2/A3/B1/B2 未被及早发现的原因。建议把这四条各补一个「必须被拦截」的断言。

### C8. 语料含元数据未定义的窗口
语料 q43 / q47 / q48 考「近 180 日」，而 `metadata.ts` 只登记了「近 90 日」口径（`trade_count_90d` / `trade_amount_90d` / `net_inflow_90d` / `outflow_amount_90d`）。模型按元数据不知道 180 日该怎么取，评测却考它。建议登记「近 N 日」的通用窗口口径。

## 六、材料口径风险（三条具体措辞）

1. **不能写**「执行准确率 100%」或「≥90%」，除非同时说明：语料自造、样本内、规划器在语料上迭代过；真正留出集是组织方问答对（尚未获得）。见 A1。
2. **不能写**「已实现表、指标、结果的合法性验证」——表/列层有缺口（A2）、指标层是死代码（A4）、结果层拦不住荒谬值（B1）。建议改为「已实现表名/列名白名单、只读单语句、行数上限等结构校验；指标层与结果层校验在补充中」。
3. **不能写**「取数 Agent 已接入平台 / 可在界面完成自然语言取数」——目前只有库函数。见 B6。
