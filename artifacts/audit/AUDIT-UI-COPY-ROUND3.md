## 一、重要（1 条）

### 重要-1　审计轨迹第 8 步仍在用绝对值口径，与主表对不上

**位置**：`lib/simulation.ts:1268`

**现状代码**：

```
result: `建议「${strategies[0].name}」：风险改善 ${(recommendedUtility.avoidance * 100).toFixed(2)}、
        人力成本 ${recommendedUtility.cost.toFixed(3)}、打扰代价 ${recommendedUtility.wake.toFixed(3)}，
        综合推荐度 ${(recommendedUtility.total * 100).toFixed(2)}`
```

**问题**：四个数全部是旧口径。以本场景推荐策略「不主动沟通」为例：

| 字段 | 审计轨迹（绝对值） | 三套方案对比主表（相对值） |
|---|---|---|
| 综合推荐度 | `−0.44`（= baseTotal×100） | **`0.00`** |
| 人力成本 | `0.004`（正数） | **`0.00`** |
| 打扰代价 | `0.002`（正数） | **`0.00`** |

两处对同一个策略给出不同的「综合推荐度」，而且**符号约定也反了**——主表把成本与打扰显示为负向扣分项，审计轨迹里是正数。

**为什么漏掉**：`执行记录` 现在包在原生 `<details>` 里，折叠状态下 `innerText` 不包含其内容，所以你的文字导出看不到这一行，也就没被发现。

**影响**：用户展开「执行记录」后，会看到与主表矛盾的推荐度数字。这正是必改-2 要消灭的「同一标签两个数」，且落在**推荐策略**这一行上，最容易对照。不误导排序决策，但会让细看的人失去信任。

**建议**：把这一处也改用 `relativeBreakdown` 的同一换算（可在 `runSimulation` 内部用与 `relativeBreakdown` 相同的公式，或以「不主动沟通」为 0 分基准计算），并把成本/打扰写成负值扣分项，与主表口径、符号完全一致。

## 三、关于「可-1 孤立的 x 是误报」

**结论可接受，但你的证据链有一处对不上，建议补一个 10 秒的确证。**

- **可信的部分**：`components/ui/progress.tsx:3` 确认它是 `@base-ui/react/progress` 的包装，`:17-24` 只做了 className 与 Track/Indicator 组合，没有插入额外文字节点；`clip-path: inset(50%)` + 1×1 + `position: fixed` 是标准的 sr-only 做法，这种元素**在构造上就不可能被用户看到**；Playwright 的 `innerText` 会把「已渲染但被裁剪」的元素计入，也是已知行为。基于这三点，按误报处理是合理的。
- **对不上的部分**：我数了导出的渲染文本，**孤立的 `x` 共 23 个**，而 `components/sandbox-app.tsx` 里字面的 `<Progress` 只有 **5 处**；同时 `MetricCard`（`:219-227`）内部并不渲染 Progress。也就是说，要么还有别的路径会渲染 Progress（经包装组件）、要么 x 另有来源。1:1 关系我没有验证出来，所以「来源就是 Progress」这一步在证据上是**未闭合**的。
- **建议的确证方式**（任选其一，10 秒）：① 放大看某几个百分比右侧，确认肉眼没有孤立字母；② 临时给 `<Progress` 加一个 `outline: 1px solid red`，看那 23 个 x 是否都落在红框内。
- **处理建议**：**不必改代码**。它是一个在构造上不可见、且不影响任何用户可见像素的节点；即使来源另有其处，只要肉眼截图干净就不构成体验问题。但请把「1:1 未验证」这一点记在心里，别把它当成已解释清楚的结论写进材料。
