# 证券客户行为沙盘 · 第一轮独立审计报告

审计对象：`securities-customer-sandbox`（v0.2.0，规则模式，未配置模型密钥）
审计方法：代码通读 + 实测探针（探针写在系统临时目录，跑完已删除，未改动任何项目文件）
审计日期：2026-09-17

---

## 总体结论：项目当前最致命的三件事

1. **合规层对模拟结果零影响。** 所谓 Policy Gateway「硬边界」，实际只改写一段展示用文本，被拦截的违规策略在数值上照常生效。关闭整个合规层，行为指标逐位相同。
2. **三套沟通策略的排序是常数写死的，不是算出来的。** 450 个扫描场景中「分群差异化沟通」450 次夺冠；「触达覆盖」这个唯一对分群不利的维度根本没进得分公式，而且连安抚效果都不受它门控。
3. **两项对外指标是同义反复。** 「规划成功率 100%」是拿常量比常量；「对照模式稳定性 1.0」是把确定性引擎重跑三遍。它们测不出任何能力差距。

这三件事都属于「材料里说了、代码里没有」，评委一旦追问就会露。

## 一、阻断级问题

### 阻断-1　合规层是装饰：拦截不改变任何数值

**位置**：`lib/simulation.ts:834-872`（先跑完数值，再做合规审查）、`lib/simulation.ts:868`（`effectiveDraftText` 只回传展示）、`lib/harness/tools.ts:245-270`

**现象**：`runSimulation` 的执行顺序是「跑完三套策略的全部数值 → 再调 `reviewCandidates` 扫描文本」。命中阻断级规则时，代码只把 `effectiveTexts[0]` 写进 `effectiveDraftText` 字段用于展示；`runStrategy` 用的是 `strategyDefinitions` 里的常数（calming / trustLift / toneRisk），与文本无关。因此被拦截的策略，其违规话术带来的数值效应原样保留。

**证据（实测）**：同一场景（跌幅 30%、48 小时、300 客户、种子 20260830）分别在合规开启与 `disableCompliance` 下运行：

```
合规开启得分: segmented=0.886639 broadcast=0.707178 baseline=0.577528
合规关闭得分: segmented=0.886639 broadcast=0.707178 baseline=0.577528
恐慌峰值 开/关: segmented 0.373006/0.373006  broadcast 0.551163/0.551163  baseline 0.559182/0.559182
```

逐位相同。广播策略那句「请务必立即行动锁定收益，本轮调整后一定反弹，不要错过这次机会」被判 3 项阻断（AD-CONTENT-02、SUITABILITY-02 等），但它的 `toneRisk: 0.055` 照旧全量作用于投诉与恐慌。

另外，`compliance.review` 工具返回 `status: 'blocked'`（`lib/harness/tools.ts:268`），但 `runner.ts:199-211` 只在审计里记下这个状态，**并不中断流水线**，后续 `report.compose` 照常执行。计划里「命中 block 时终止该策略」没有实现。

**影响**：`README.md:26-31` 写「由合规硬边界负责（模型不可绕过）……命中阻断级规则时强制改写或拦截该策略」，与实现完全不符。这是全项目最容易被评委当场击穿的一处。

**修复方向**：
1. 把合规审查移到策略生成之后、数值模拟之前，让 `effectiveDraftText` 真正成为模拟的输入（至少让 `toneRisk` 由被拦截文本决定，阻断后归零）。
2. 策略级阻断应跳过该策略的模拟，标记为「已阻断，不参与排序」。
3. 若短期内不打算改架构，必须把 README 与材料改为「合规层对策略文本做拦截与改写并留痕，不改变群体行为数值；行为与合规两层解耦」——但这样就等于承认它不是硬边界。

### 阻断-2　三套策略结构上必然同序，且覆盖维度完全失效

**位置**：`lib/simulation.ts:207-251`（三套策略的四个常数）、`lib/simulation.ts:765-767`（得分公式）、`lib/simulation.ts:674-676`（安抚无条件作用于全体客户）、`lib/simulation.ts:739`（coverage 唯一使用点）

**现象**：三套策略只差四个常数。得分公式为

```
score = 0.84 - 峰值恐慌×0.27 - 期末卖出×0.25 - 期末投诉×0.20 - 期末流失×0.12 + 期末信任×0.16
```

`coverage` 不在其中。更严重的是：安抚项 `targetedBoost` 对**每一个客户、每一个时间步**无条件生效（第 672-707 行的循环里没有任何 reach 判断），`strategy.coverage` 在整个引擎中**只出现在第 739 行**——用于生成给界面画进度条的快照值。也就是说，覆盖率既不影响客户是否收到安抚，也不影响得分，是一个纯装饰数字。

**证据（实测 450 场景扫描）**：跌幅 5/10/20/30/50% × 时长 6/24/48/72/168h × 步数 5/10/20 × 种子 3 个 × 客群 2 种

```
segmented: 450 (100.0%)
冠军-亚军分差: 最小 0.0431  中位 0.1200  最大 0.3236
```

不是险胜，是结构性压制。补充实测：期末 coverage 为 segmented 0.920、broadcast 1.000、baseline 0.086——广播策略覆盖最高却排第二。

另有一处隐藏优势：分群策略的 `trustLift: 0.095` 在 10 步累计后信任恒被 clamp 到 1.0，**信任项对分群策略永远拿满分 0.16**，与场景无关。

**影响**：「策略比较」这张表不具备产生不同结论的能力，只能演示一个预设排序。界面上「触达覆盖」柱状图显示广播 100%、分群 92%，结论却是分群更优——图表和结论自相矛盾。

**修复方向**：见第三章「沟通策略重做方案」。

### 阻断-3　规划成功率 100% 是同义反复

**位置**：`scripts/eval-plan.ts:58`（`expectedTools = planSteps.map(...)`）、`scripts/eval-plan.ts:93`（比对）、`lib/harness/planner.ts:13-30`（`canonicalSteps` 与 `defaultPlan`）、`lib/harness/planner.ts:202`（`planSteps`）、`lib/harness/planner.ts:47-72`（`validatePlan`）

**现象**：评测的「期望工具集」取自 `planSteps`，而 `planSteps` 和 `defaultPlan()` 都是同一份 `canonicalSteps` 常量的 `map` 结果。评测又用 `config: null` 调用（`eval-plan.ts:66`），必然走 `defaultPlan()`。拿常量比常量，恒为真。

即使接上真实模型也不成立：`validatePlan` 在校验通过后会把模型输出**强制重排**成 `canonicalSteps` 的顺序（第 65-69 行），模型只贡献 `title` 与 `intent` 两段文本。模型若漏掉任一工具或顺序不对，`provided.size < canonicalSteps.length` 直接返回 null，回落到同一份 `defaultPlan()`。**任何路径下工具序列都完全相同。**

**证据（实测）**：

```
defaultPlan 工具序列 == planSteps: true
planTask 工具序列    == planSteps: true
```

另外 `eval-plan.ts:122` 的通过判定是 `planSuccessRate >= threshold && toolSuccessRate >= threshold`，**没有把场景抽取成功率纳入**——抽取全错也算通过。

**影响**：`artifacts/指标证据表.md:22`「标准任务规划与工具调用成功率 100%」与申报书中的对应表述，实际只是「确定性流水线 20 次都跑完了」的冒烟测试。项目最核心的「Agent 自主规划」卖点，目前没有任何指标支撑。

**修复方向**：
1. 评测改为**不看工具序列**，改看模型是否真的产出了被采纳的结构：以「模型输出被采纳的比例」和「降级为模板的比例」为主指标。
2. 若要让规划真正可变，`validatePlan` 必须允许步骤增删与重排（只校验工具合法性），而不是把结果钉死在同一序列。
3. 无论如何，先把「100%」从材料里拿掉，改为「20 个标准任务端到端成功率 100%（规划为确定性模板，见口径说明）」。

### 阻断-4　合规发现与合规风险在所有场景下完全相同

**位置**：`lib/simulation.ts:354-375`（原型风险等级与产品风险等级两张独立表）、`lib/simulation.ts:465`（`products[index % 4]`）、`lib/simulation.ts:857-861`（按规则去重只留一条）

**现象**：客户持仓按下标轮转分配，与客户原型的风险等级毫无关系。原型风险等级是 C2/C3/C4/C5，产品风险等级是 R2/R3/R4/R5，两者独立抽样，必然产生适当性错配。`suitabilityFinding` 再按规则去重，只保留一条，掩盖了规模。

**证据（实测，300 名客户）**：阻断级错配（产品风险 − 客户等级 ≥ 2）**129 名**，复核级 66 名。因此 `SUITABILITY-MATRIX-01` 必然触发。

三个差异极大的场景（5%/24h/300人、30%/72h/300人、50%/168h/500人）实测结果完全相同：

```
规则集合: AD-CONTENT-01/提示, RISK-DISCLOSURE-02/提示, SUITABILITY-02/提示, SUITABILITY-MATRIX-01/阻断, SUITABILITY-MATRIX-02/警告
各策略合规风险: segmented=高 broadcast=高 baseline=高
发现数: 5 / 5 / 5
```

**影响**：界面的「合规发现」永远显示同样的 5 条、永远含 1 项阻断，审计轨迹第 7 步永远是 `status=blocked`。合规展示退化为静态内容，无论业务输入如何变化。这正是「结构性必然结论」的典型。

**修复方向**：客户风险等级应与持仓产品挂钩（按等级匹配可选产品集合），让错配成为**可变量**——例如只有少数客户因历史原因持有越级产品。修复后，合规发现数应当随客户结构与场景变化。

### 阻断-5　对照实验不随场景变化，「稳定性」恒等于 1

**位置**：`lib/baselines/compare.ts:39-56`（关键词打分）、`lib/baselines/compare.ts:80-84`（`stabilityOf`）、`lib/baselines/compare.ts:106`、`lib/baselines/compare.ts:116`、`lib/baselines/compare.ts:130-131`、`lib/baselines/compare.ts:164-167`

**现象**：
- `llm-only` 与 `llm-rag` **完全不调用模型**。它们用 `strategyHints` 关键词子串计数给策略打分（第 47-56 行）。两个模式的唯一差别是 `knowledgeCoverage` 是否把检索到的语料算进去，且条件是与策略文本同时命中——策略文本是固定的，所以这只相当于给所有策略加同一个偏移量。
- `stabilityOf` 把同一个场景用同一个种子跑 `repeats` 次，取 `1 / 唯一签名数`。引擎是确定性的，签名必然全同，**稳定性恒为 1**，四种模式都是。这个指标没有任何信息量。
- `single-agent` 与 `dual-layer` 的排序一致率都是 100%，因为两者都恒选 segmented（见阻断-2），一致率是必然结果而非能力体现。

**证据（实测，两个差异极大的场景）**：

```
跌幅 10% / 24h          跌幅 40% / 96h
llm-only      broadcast  0.6667  稳定=1   |  llm-only      broadcast  0.6667  稳定=1
llm-rag       broadcast  0.6667  稳定=1   |  llm-rag       broadcast  0.6667  稳定=1
single-agent  segmented  1.0     稳定=1   |  single-agent  segmented  1.0     稳定=1
dual-layer    segmented  1.0     稳定=1   |  dual-layer    segmented  1.0     稳定=1
```

两列逐字相同。

**影响**：`artifacts/指标证据表.md:67-76` 的对照表无法支撑「分群干预价值需要数值模拟才能识别」这个结论——因为前两行根本不是模型，后两行的 100% 是常数决定的。

**修复方向**：接入真实模型后重跑；`stability` 改为对**不同种子**的稳定性（把种子当作随机扰动来源重采样），或直接删掉该指标。对照结论必须基于真实模型输出。

## 二、重要问题

### 重要-1　Skill 审批是死功能：批准不被复用，回滚必然失败

**位置**：`lib/harness/runner.ts:240-266`（`version: 1` 写死）、`app/api/skills/[id]/[action]/route.ts:34-43`（回滚查询）、`components/sandbox-app.tsx:713`、`README.md:41`

**现象**：任务成功后确实会写一条 `candidate` 技能，但：
- 全仓库没有任何代码读取 `skills` 表用于规划或执行。`rg` 全量检索确认，「消费方」只有列表接口与前端页面。
- `version` 永远是 `1`（`runner.ts:244`），而回滚要查 `version < current.version` 的记录，永远查不到。

**证据（对运行中的服务实测）**：
```
POST /api/skills/b900df63-.../rollback
{"error":"该技能没有更早的版本。"}   HTTP 409
```
数据库中 15 条技能，`version` 全为 1。

**影响**：三处声明不成立——`components/sandbox-app.tsx:713` 的「人工审批后才可被后续任务复用」、`app/api/skills/[id]/[action]/route.ts:7` 的同一句话、`README.md:41` 的「版本回滚」。按当前实现，「回滚」是一个点了必然报错的按钮。

**修复方向**：要么实现（批准后按场景相似度命中并注入规划；同名技能二次生成时 `version + 1`），要么把三处文案改为「提供候选技能的批准、拒绝与归档留痕；技能复用与版本回滚列入决赛阶段」。**不要保留现状。**

### 重要-2　`result.findings` 只含推荐策略，与审计口径冲突

**位置**：`lib/simulation.ts:877`（`findings = recommendedRun.result.findings`）与 `lib/simulation.ts:878-880`（`allFindings` 用于审计计数）

**现象**：同一个结果对象里存在两种口径。`result.findings` 只取推荐策略的发现；审计第 7 步的「N 项阻断」却来自全部三套策略。

**证据（实测同一场景）**：
```
result.findings: 5 条，只涉及「分群差异化沟通」，其中阻断 1 条
审计 seq 7: "5 项阻断、4 项待审批"   ← 含广播策略的 3 条真实阻断
```

**影响**：界面「合规发现」卡片显示 1 项阻断，下方审计轨迹写「5 项阻断」，同一屏两个数字打架。而且被拦截最严重的广播策略（9 条发现、3 条阻断）在发现列表里完全看不到。

**修复方向**：`result.findings` 改为全部策略的发现（或在卡片上按策略分组展示），审计计数与展示口径统一。

### 重要-3　客群口径与文档不符：「回撤 ≥ 8%」实际是「holdingBeta ≥ 0.8」

**位置**：`lib/scenario.ts:37-41`、`lib/simulation.ts:506-509`、`lib/simulation.ts:473-474`

**现象**：筛选条件是

```
holdingBeta >= segmentBetaThreshold   // 0.8
holdingBeta = 0.62 + 野心×0.42 + 从众×0.24 - 纪律×0.16 + (波动率-1)×0.55 + 扰动
drawdown    = 跌幅×100 × holdingBeta + (random()−0.5)×3
```

筛选用的是 beta，而真实回撤还叠加了 ±1.5 个百分点的个体扰动。被选中的客户实际回撤可能低于 8%，反之亦然。

**证据（实测，跌幅 10%、种子 20260830）**：
```
入选 300 名中，实际回撤 < 8% 的: 24 名 (8.0%)
单块 300 名中，回撤 >= 8% 却被排除的: 11 名
例：C-1009 回撤 7.5% beta 0.84 产品 新能源主题基金
```

**影响**：`README.md:133` 与 `artifacts/指标证据表.md:51` 都写「回撤不低于 8%」，与实现有 8% 左右的偏差。金额不大，但属于「写的和做的不是一回事」。

**修复方向**：二选一。① 文案改为「按 10% 基准冲击下的持仓弹性 beta ≥ 0.8 筛选，等价于回撤主项不低于 8%（不含 ±1.5pp 个体扰动）」；② 直接把筛选条件改成真实回撤比较，并在 `customer.staging` 阶段就固定住。

### 重要-4　`disablePsychology` 消融不彻底

**位置**：`lib/simulation.ts:520-527`（`flattenPsychology`）、`lib/simulation.ts:467-472`（holdingBeta 由心理参数算出）

**现象**：关闭心理层时，只把六维心理替换为 0.5 并重算 panic，但 `holdingBeta` 和 `drawdown` 是在 `generateCustomers` 阶段**用心理参数算出来的**，没有被重算。心理层通过持仓弹性继续影响回撤与初始恐慌。

**影响**：`artifacts/指标证据表.md:60`「关闭心理层 −1.83 个百分点」低估了心理层的真实贡献，消融结论偏保守。这是个方法论问题，评委若懂实验设计会追问。

**修复方向**：`flattenPsychology` 中一并按平坦心理重算 `holdingBeta` 与 `drawdown`。

### 重要-5　客户「记忆」里的历史事实是心理常数反推的

**位置**：`lib/harness/memory.ts:27-36`

**现象**：
```
`历史回撤超过 ${drawdown}% 时倾向快速赎回，近 30 日出现 ${Math.round(herding*6)} 次高频查看净值。`
`同群情绪变化时咨询量上升约 ${Math.round(herding*40)}%。`
`近 30 日无主动咨询记录，……`
```
这些数字来自 `herding × 6`、`herding × 40` 这样的算式，不是任何观测记录，但被表述成「近 30 日」的历史事实。

**影响**：README:38 与界面把它叫「客户记忆」。虽然数据源已声明为合成，但「把参数反推值写成历史观测」容易被读成伪造数据。

**修复方向**：措辞改为倾向性描述（「该画像在社交渠道获取信息较多，同群情绪波动时咨询量上升明显」），去掉具体天数与次数；或在界面上标注「由心理参数派生」。

### 重要-6　审计第 8 步是写死的文案，Reflector 不是独立模块

**位置**：`lib/simulation.ts:890-891`、`lib/harness/runner.ts:240-266`

**现象**：`{ seq: 8, actor: 'Reflector', action: '生成反思与候选技能', … }` 写在 `runSimulation` 里，是一条固定字符串。真正写技能的是 `runner.ts` 里的一段内联代码。所谓「反思」没有独立的判断逻辑，既不评估本次结果好坏，也不决定是否该沉淀。

**影响**：界面与材料呈现为「Reflector 生成反思与候选技能」，实际每次任务无条件写一条。

**修复方向**：要么把 `proposeSkill` 的触发条件显式化（例如仅当指标优于已批准技能快照时才提议），要么在材料中改称「任务成功后自动沉淀候选技能」。

### 重要-7　材料内部自相矛盾：合规层「不可绕过」vs「不影响群体指标」

**位置**：`README.md:26-31` 与 `artifacts/指标证据表.md:63-65`

## 四、沟通策略重做方案

### 4.1 现状诊断

现有建模的失效不在参数取值，而在**结构**：三套策略只差四个标量；得分公式恰好只包含分群策略占优的三个维度；唯一对分群不利的覆盖维度既不进公式、也不门控安抚。任何调参都无法让排序随场景变化，因为排序由常数直接决定。

### 4.2 建议方案：参数空间 + 网格搜索，三套策略降为锚点

**推荐改为「策略参数空间 + 引擎搜索」**，理由：

1. 排序由引擎算出来，而不是由常数写出来——这从根上消除「结论写死」的问题。
2. 让大模型真正进入决策：LLM 不再生成无关痛痒的文案，而是**根据业务目标设定效用权重 λ**（预算紧不紧、更怕流失还是更怕投诉），引擎在参数空间里搜最优。这正好落在「LLM 负责目标理解与解释、数值模型负责计算」的原则上。
3. 评委的追问可以现场回答：「预算翻倍会怎样」「时间窗只有 6 小时怎么办」——改 λ 或场景重跑即可。
4. 成本可接受：引擎 300×10 约 17 ms，3×3×3=27 个候选点全跑约 0.5 秒。

三套固定策略保留为**锚点展示**（演示叙事需要三个有名字的方案），但它们只是参数空间里的三个点。

### 4.3 策略参数向量

每套策略是一个五维点：

| 参数 | 含义 | 建议范围 |
|---|---|---|
| `r` | 触达覆盖率 | 0—1 |
| `d` | 人工深度（0=纯自动消息，1=客户经理逐人沟通） | 0—1 |
| `p` | 内容个性化程度 | 0—1 |
| `rampSteps` | 达到目标覆盖率所需步数（由 d 决定的人工作业排队时间） | 1—6 |
| `w` | 唤醒系数（主动触达本身引起的额外关注/焦虑） | 0—0.05 |

锚点取值：

| 锚点 | r | d | p | rampSteps | w |
|---|---|---|---|---|---|
| 不主动沟通 | 0.08 | 0.00 | 0.00 | 0 | 0 |
| 统一风险提示 | 0.95 | 0.05 | 0.10 | 1 | 0.050 |
| 分群差异化沟通 | 0.86 | 0.45 | 0.90 | 4 | 0.023 |

### 4.4 引擎改造公式

设客户 i 在步 t 的恐慌为 `panic_i(t)`，优先级为 `prio_i`。

**(1) 逐客户触达门控（替换现在无条件生效的安抚）**

```
reach_i(t) = min(1, t / rampSteps) × (prio_i = 高 ? min(1, r×1.15) : r×0.75)
```

这一步同时修掉阻断-2：安抚从此只对被触达的客户生效。

**(2) 安抚强度（覆盖 × 深度 × 个性化）**

```
match_i     = 1 − |客户风险等级 − 策略目标风险等级| / 4        ∈ [0,1]
boost_i(t)  = reach_i(t) × ( 0.10×d + 0.12×p×match_i )
```

d=0.45、p=0.90、match=1 时约 0.153/步，且随 rampSteps 爬升——不再开局即满效。

**(3) 唤醒效应（新增，制造「小跌不打扰」的真实取舍）**

```
wake_i(t) = w × (1 − panic_i(t−1)) × 1{本步首次触达}
```

低恐慌客户被主动联系后会提高关注度。群发泛化消息 w=0.05 更扰民，个性化沟通 w=0.023 更温和——个性化因此有了可解释的价值来源。

**(4) 触达成本**

```
unitCost_i = 1 × (1 + 24×d)                        单位＝一条 App 消息
cost(s)    = Σ_t Σ_i unitCost_i × reach_i(t) / customerCount
```

d=0.05 → 2.2；d=0.45 → 11.8。分群策略成本约为广播的 4.5 倍、不沟通的百倍以上。这是现实中「不能对所有人做一对一」的真实代价。

**(5) 效用函数（替换现有 0.84 常数式打分）**

```
避险收益(s) = 0.30×(基线恐慌峰值 − 本策略恐慌峰值)
            + 0.30×(基线卖出 − 本策略卖出)
            + 0.25×(基线流失 − 本策略流失)
            + 0.15×(基线投诉 − 本策略投诉)

U(s) = λ_avoid × 避险收益(s) − λ_cost × cost(s) − λ_wake × 唤醒总量(s)
```

默认 `λ_avoid=1、λ_cost=0.35、λ_wake=0.25`，**由大模型依据业务目标给出**（这是 LLM 在本模块的真实职责）。

改成「相对不干预基线的增量」还有一个附带好处：消除了现在 0.84 常数把最差方案抬到 0.5775 的语义混乱。

### 4.5 预期结论分布（需实测确认）

| 场景 | 预期夺冠 | 机制 |
|---|---|---|
| 5% 微跌 | 不主动沟通 | 唤醒代价 > 安抚收益 |
| 10—20% 中等跌幅 | 统一风险提示 | 成本低、覆盖高、唤醒可接受 |
| ≥30% 且步数 ≥10 | 分群差异化沟通 | 情绪扩散需要点对点阻断 |
| 6 小时 / 5 步短窗口 | 统一风险提示 | 分群需要 4 步爬坡，来不及 |
| λ_cost 调高（预算收紧） | 统一风险提示 | 人工成本超过收益 |
| 高流失倾向客群占比高 | 分群差异化沟通 | 流失代价权重放大 |

关键在于「哪种策略最优」开始随场景与目标变化。

### 4.6 验收标准

1. **扫描 ≥ 200 个场景**（跌幅 5—50% × 时长 6—168h × 步数 5—20 × 客群 2 种 × 种子 ≥3），三个锚点**都必须有夺冠记录**，且每种夺冠场景占比 ≥ 10%。
2. **敏感性可解释**：跌幅单调下降时结论应从「分群」移向「不主动沟通」；`λ_cost` 单调上升时结论应从「分群」移向「广播」。
3. **单一参数不得翻转结论**：敏感性分析显示结论需 ≥2 个参数联合变化才会翻转，避免再次出现「一个常数决定答案」。
4. **同种子复现**：聚合签名不变。
5. **每次推荐必须输出归因分解**（避险收益 / 成本 / 唤醒三项数值），且分解与两个被比较场景的差异方向一致。
