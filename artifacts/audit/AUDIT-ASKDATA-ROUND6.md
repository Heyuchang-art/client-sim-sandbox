## 三、仍未覆盖：两张 1:n 表同时参与的多指标（E）

**为什么会漏**：`planner.ts:432-439` 的 `isolated()` 只把 **1:1 表**上的聚合改成相关子查询；遇到 1:n 表时 `:437` 直接 `return aggregate`（保持原样）。于是改写后的内层 SQL 仍然是 `FROM cust_info c JOIN cust_holding h ... JOIN cust_trade t ... GROUP BY c.cust_id`，**两张 1:n 表在内层互相交叉**（每位客户产生 n_h × n_t 行），两个 SUM 都被对方的行数放大，外层再 SUM 一次。

实测（期望值均由我在单表上独立算）：

| 问法 | 我的独立期望 | 规划器实际 | 偏差 |
|---|---|---|---|
| 持仓市值与交易金额 | 8,066,582,414 / 16,813,099,811 | **43,046,684,567** / **41,847,820,017** | ×5.34（+433.7%）/ ×2.49（+148.9%） |
| 持仓成本与交易金额 | 9,357,818,956 / 16,813,099,811 | **51,525,482,412** / 41,847,820,017 | ×5.51（**+450.6%**） |
| 持仓市值与净流入 | 8,066,582,414 / −215,160,299 | **19,779,122,242** / **−817,711,182** | ×2.45 / ×3.80 |
| 持仓市值与近 90 日交易金额 | 8,066,582,414 / 3,902,881,033 | 9,748,321,627 / **10,185,319,646** | ×1.21 / ×2.61 |
| 客户近 30 日的交易金额和净流入 | 1,307,623,955 / 11,770,727 | 241,876,295 / 10,046,079 | ×0.18 / ×0.85 |

生成的 SQL 形态（可见内层两张 1:n 表并列）：

```sql
SELECT SUM(t.m0) AS 交易金额, SUM(t.m1) AS 持仓市值合计 FROM (
  SELECT c.cust_id AS cust_id, SUM(t.trade_amount) AS m0, SUM(h.market_value) AS m1
  FROM cust_info c JOIN cust_holding h ON c.cust_id = h.cust_id
                  JOIN cust_trade t ON c.cust_id = t.cust_id
  GROUP BY c.cust_id) t LIMIT 10
```

**同族第二例（E2）**：内层用 `JOIN`（内连接）会把**没有该明细记录的客户整行丢掉**。实测「总资产与持仓市值与交易金额」→ 总资产 11,224,575,855，而我的独立值是 11,780,575,938（−4.7%）；差额正好等于 82 名无交易客户的资产（我实测：有交易记录的客户总资产 = 11,224,575,855）。这条在改写前后都存在，改写后误差方向从 +29% 变成 −4.7%，同样是错的。

**这两条都未被三档语料覆盖**（语料里没有「两张明细表并列」的多指标题），所以 50/50、15/15、12/12 全绿并不代表这一类是安全的。

**最小复现与修复方向**
- 复现：`持仓市值与交易金额`（无任何筛选条件，最干净）→ 43,046,684,567 / 41,847,820,017。
- 修复方向：把 `isolated()` 同样应用到 1:n 表 —— 每个指标都写成按客户的相关子查询，例如 `SUM((SELECT SUM(h.market_value) FROM cust_holding h WHERE h.cust_id = c.cust_id))`；这样内层不再需要 `JOIN` 两张明细表，`E2` 的丢客户问题也一并消失。若指标自带明细表筛选（例如流水时间窗），把该条件推进对应指标的子查询；推不进去时沿用现有的拒答策略。
