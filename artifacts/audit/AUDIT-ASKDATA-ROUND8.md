## 二、改动 1：G-RES-08 → 核对属实

实现：`guardrail.ts:241-259`。判定步骤是「本次 SQL 用到的表里存在 1:n 明细表」+「出现了 `SUM|AVG(<别名>.)` 且该别名指向 1:1 表」+「该聚合不在 `(SELECT ...` 的相关子查询里」，命中给 `layer: '结果'、disposition: '提醒'`。

`SUM(h.market_value)` + 1:n 表 → 不触发 ✓；`SUM(a.total_asset)` 无 1:n 表 → 不触发 ✓；`COUNT(DISTINCT c.cust_id)` + 1:n 表 → 不触发 ✓。

### 是否会对规则路径自身输出造成误报 → 不会

- 我扫描了三档语料 **77 条**：`G-RES-08 触发 0 次`（样本内 0、留出集 0、边界集 0）。
- 另外抽查 5 条最可能触发的问法（`有持仓记录的客户总资产是多少`、`有交易记录的客户总资产是多少`、`主办关系的客户总资产是多少`、`客户总资产与持仓市值`、`持有科技成长组合的客户总资产是多少`）→ 全部无提醒。
- 原因不是巧合：这类问法在规划器里要么走了按客户收敛的改写（`SUM((SELECT ...))` 落在 `(SELECT` 之内被排除），要么因为「有持仓记录」同时命中 `holding_count` 指标而进入多指标改写路径（例如 `有持仓记录的客户总资产是多少` 实际生成 `SELECT SUM(t.m0) AS 总资产合计, SUM(t.m1) AS 持仓笔数 FROM (SELECT c.cust_id, (SELECT SUM(a.total_asset) ...) AS m0, COUNT(*) AS m1 ...) t`）。**结论是结构性的，不是碰巧。**

### 精度上的两点（都是「提醒」级，不影响正确性）

**(a) 可误报：1:n 表只出现在 IN / EXISTS 子查询里（没有连接）时也会触发**
- 最小复现：`SELECT SUM(a.total_asset) AS t FROM cust_info c JOIN cust_asset a ON c.cust_id = a.cust_id WHERE c.cust_id IN (SELECT cust_id FROM cust_holding) LIMIT 10` → 触发 G-RES-08（`EXISTS` 变体同样触发）。
- 但这条 SQL 实际上**没有连接放大**（子查询不参与聚合），所以是误报。影响仅限「审计里多一条提醒」，不会拦截、不会改数字。
- 规划器不会产出这种形态（我扫了 77 条语料 0 命中），所以只有模型路径手工写这种 SQL 时才会看到。
- 修复方向（如果要收紧）：把「1:n 表存在」改为「1:n 表与风险聚合处于**同一层 FROM/JOIN**」，例如只在风险聚合所在 SELECT 的顶层 FROM 列表里检查 1:n；或者反过来，把「风险聚合前面的 80 字符看是否在 `(SELECT` 内」的排除扩展到「是否在任何子查询内」。

**(b) 可漏报：逗号连接形式不触发**
- 最小复现：`SELECT SUM(a.total_asset) AS t FROM cust_info c, cust_holding h, cust_asset a WHERE ...` → 不触发 G-RES-08。
- 但它**同时被拦截级规则挡下**：实测 `passed=false`，命中 `G-SEM-05 + G-SEM-06 + G-SEM-03`（逗号连接不进 `extractTableRefs` 的别名映射，`h.` / `a.` 被当成未知引用）。因此这个漏报不可利用，不需要修。
