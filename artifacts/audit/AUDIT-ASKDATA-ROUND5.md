### 但 F1 的改动新引入两条问题

#### A（阻断级，新引入）分组被静默丢掉，分组问题被当成总量问题回答

- 问法：「各客群标签的总资产与持仓市值」

- 代码：`planner.ts:395` 判定 `needsScalar` 后，`planner.ts:417-423` 直接返回，SQL 里没有 `GROUP BY`（`:418`），返回体写死 `dimension: null`（`:421`）。该分支在 `grouped` / `dimension` 已算出的情况下仍无条件生效。
- 影响：用户问「各客群标签的…」拿到的是全体合计，既没有分组也和问题不符，而**围栏放行、语料也测不到**（语料 q40 是 AVG 口径，`:408` 会退回连接形态，所以掩盖了这个分支）。

#### B（重要，新引入）户均 + 多指标跨表会拼出语法错误的 SQL

- 问法：「户均总资产与户均持仓市值」
- 实际 SQL：`SELECT SUM((SELECT CAST(SUM(h.market_value) FROM cust_holding h WHERE h.cust_id = c.cust_id)) AS REAL) / COUNT(DISTINCT c.cust_id) AS 户均持仓市值, ...`
- 运行结果：`notes=["未配置模型密钥，使用规则取数。","执行失败：near \"FROM\": syntax error"]`，`mode=degraded`，返回空结果。**围栏 `passed=true` 没拦住。**
- 代码：`planner.ts:399-401` 的 `/^([\s\S]*?)\s+AS\s+([\s\S]+)$/` 在已含 `CAST(...) AS REAL` 的表达式上匹配到**第一个** ` AS `，把聚合体截成 `CAST(SUM(a.total_asset)`、把后半段当成输出标签；`:409` 的 `/^\s*(SUM|COUNT|CAST)\s*\(/` 又恰好放行 `CAST(`，于是拼出括号不闭合的 SQL。
- 影响：不是静默错误数字（执行失败会走降级），但属于本轮新引入的功能缺陷，且说明 scalar 改写与 ROUND3 的 per-capita 改写（`planner.ts:354-362`）叠加时没有被覆盖测试。
- 修复方向：改写前先按**最外层** ` AS ` 拆分（例如用「最后一个 ` AS `」或改按 `metric.label` 匹配），或在 `perCapita` 命中时禁用 scalar 改写。

## 四、仍未修的"会主动输出错误数字"路径

### C（阻断级，未修）单指标跨表 SUM 仍被连接放大

- 问法：「持有科技成长组合的客户总资产是多少」（**正是语料 q24 的形态**）
- 规划器 1,383,683,594 vs 我去 fan-out 算出的真值 1,127,949,184 → **+22.7%**
- 代码：`planner.ts:395` 的 `expressions.length >= 2 && measureAliases.size >= 2` —— scalar 改写**只在 ≥2 个指标时才触发**。单指标时如果 FROM 里被筛选条件拉进了明细表（产品筛选 → `cust_holding` + `prod_info`），`SUM(a.total_asset)` 仍按持仓行数重复计入。
- **连带问题**：语料 q24 的黄金 SQL 是同一个连接形态，因此**黄金答案同样偏大 22.7%**，三档评测照不出来（评测与实现同源）。这条我在 ROUND1 的 15 条语料检查里看过"golden 能执行、列名对齐"，但没做"golden 语义是否被 fan-out 污染"的独立复算，属于我的漏检。
- 修复方向：把 scalar 改写的触发条件从「≥2 指标」放宽为「表达式里 SUM 的表是 1:1 表（cust_asset/cust_info）且 FROM 中存在 1:n 表」，或对 `SUM(a.*)` / `SUM(c.*)` 统一改写；同时把 q24 的黄金 SQL 改成去 fan-out 的形态。

### D（阻断级，未修，与 F2 同族）非资产类数值阈值被静默忽略

阈值解析只认 `(总)资产`，其他指标的数值条件既没进 `where` 也没触发拒答：

| 问法 | 规划器返回 | 真值（我独立算） |
|---|---|---|
| 持仓市值超过 100 万的客户有多少人 | `{持仓市值合计: 8066582414, 客户数: 1000}` | 269 |
| 交易金额超过 500 万的客户有多少人 | `{交易金额: 16813099811, 客户数: 918}` | 560 |
| 近 30 日交易金额不低于 100 万的客户有多少人 | `{交易金额: 1307623955, 客户数: 309}` | 283 |
| 净流入超过 10 万的客户有多少人 | `{净流入: -215160299, 客户数: 952}` | 440 |
| （对照）总资产超过 1000 万的客户有多少人 | 198 | 198 ✓ |

- 危害在于**返回体里带着一个 `客户数` 字段**（1000 / 918 / 952 这些是"全部客户"或"有交易记录的客户"），用户很容易把它读成"满足阈值的人数"，而真实答案（269 / 560 / 440）相差 1.3–3.7 倍。
- 修复方向：把阈值提取从 `(?:总资产|资产)` 扩展到持仓市值 / 交易金额 / 净流入 / 持仓成本等金额指标；或者只要检测到「金额指标 + 比较词 + 数字」而无法下推，就明确拒答（与 F1 的拒绝策略一致）。
